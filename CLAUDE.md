# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

An Upwork portfolio monorepo: three self-contained AI automation MVPs built as **n8n workflows** on a shared Docker Compose stack (n8n, PostgreSQL+pgvector, Mattermost, NocoDB, Mailpit, and a Python/FastAPI OCR service). Each `NN-*/` project folder holds its workflow JSON, samples, demo script, `docs/architecture.md`, screenshots, and `UPWORK.md` (the copy for the Upwork portfolio entry). Repo content and deliverables are in English. `docs/privado/` is gitignored personal notes — never reference it in published files.

## Commands

```bash
cp .env.example .env && ./scripts/bootstrap.sh   # full stack setup; idempotent, safe to re-run
./scripts/import-workflows.sh                    # re-import + publish all workflows after editing JSON
docker compose up -d --build extractor           # rebuild the OCR service after changing it

# Demos (run against the live stack; --reset clears that project's DB rows, alerts, CRM/email)
./01-ai-lead-qualification/scripts/demo.sh [--reset]
./02-ai-document-extraction/scripts/demo.sh [--reset]
./03-ai-support-knowledge-base/scripts/ingest-kb.sh   # must run before project 03 demo/eval
./03-ai-support-knowledge-base/scripts/demo.sh
./03-ai-support-knowledge-base/scripts/eval.sh        # accuracy over samples/eval-questions.json (currently 12/12)

# Extractor tests (inside the container, which has Tesseract + fonts the tests need)
docker compose exec extractor pytest
docker compose exec extractor pytest tests/test_extract.py::test_health

# DB access
docker compose exec postgres psql -U portfolio -d portfolio
```

Project 02 sample documents are generated by `02-ai-document-extraction/samples/generate_samples.py`.

## Architecture

**Workflows are the source of truth as JSON in git.** `import-workflows.sh` stops n8n, imports and publishes every `shared/workflows/*.json` and `NN-*/workflows/*.json` in a one-off container, restarts n8n, then waits until every webhook path is registered *and* n8n's `workflow_published_version` matches `activeVersionId` (n8n briefly serves the old version after restart). Edits made in the n8n UI are lost unless exported back to the JSON file. Workflow `id`s are fixed strings (e.g. `leadQualify00001`) so re-imports overwrite in place.

**Conventions every workflow follows** (keep them when adding/changing workflows):
- Entry point is a webhook (`lead-intake`, `invoice-intake`, `kb-ingest`, `support-ask`) authenticated by the `X-Webhook-Token` header compared to `$env.WEBHOOK_TOKEN`, then a Code node validates input and returns `4xx` with field errors via Respond to Webhook.
- Configuration comes from env vars read as `$env.*` (enabled by `N8N_BLOCK_ENV_ACCESS_IN_NODE=false`). A new variable must be added to `.env.example` **and** to the `n8n` service `environment:` in `docker-compose.yml`, or the workflow won't see it.
- OpenAI is called with plain HTTP Request nodes (not LangChain/AI nodes), with strict JSON-schema output, `retryOnFail`, and `onError: continueErrorOutput` wired to a fallback branch (manual review / escalation) so data is never lost when the AI is down. Business decisions (thresholds, routing, guardrails) are made in Code nodes, not by the model.
- Credentials are referenced by fixed IDs created by `bootstrap.sh`: `pgPortfolio00001` (Postgres) and `smtpMailpit00001` (Mailpit SMTP). Mattermost/NocoDB are called via HTTP with env-provided URLs/tokens.
- `settings.errorWorkflow = errHandler000001` → `shared/workflows/global-error-handler.json`, which writes to `automation_errors` and posts to Mattermost with a link to the failed execution.
- Every request writes a row to the shared `execution_log` table (status `success|rejected|duplicate|failed`, latency, model, tokens), tagged by `project` (e.g. `01-lead-qualification`). Idempotency/duplicate checks happen before any AI call.

**Database:** Postgres hosts separate DBs `n8n`, `mattermost`, `nocodb` (`00-databases.sql`) plus business data in `POSTGRES_DB` (`portfolio`). Schemas live in `infra/postgres/init/`: `01-shared.sql` (observability) and one `N0-*.sql` per project. Init scripts only run on an empty volume, so `bootstrap.sh` re-applies `[1-9]*.sql` every run — **all schema SQL must be idempotent** (`IF NOT EXISTS`, etc.). New project → add `N0-<name>.sql`.

**Networking:** inside containers services are reached by compose name (`http://extractor:8000`, `http://mattermost:8065`, `http://nocodb:8080`, `mailpit:1025`); from the host Postgres is on port `5433`. The repo is mounted read-only into n8n at `/portfolio`.

**Project specifics** (details in each `docs/architecture.md`):
- **01** lead → validate → dedupe → AI score → rules (`HOT/WARM_LEAD_THRESHOLD`) → Postgres + NocoDB CRM + Mattermost/email by route.
- **02** upload → `extractor` service (`/extract`: pdfplumber text layer, falls back to Tesseract OCR `eng+spa`) → AI field extraction → math check with `INVOICE_AMOUNT_TOLERANCE` → duplicates/mismatches to human review.
- **03** two workflows: `kb-ingestion` (chunk by `##` section, SHA-256 skip-unchanged, atomic chunk replace, pgvector HNSW) and `support-assistant` (embed → top-K search → below `RAG_MIN_SIMILARITY` escalates without LLM → grounded answer with citations → code guardrails). Holding replies match the customer's language (Spanish/English).

The Mattermost team is `acme` with channels `sales-alerts`, `ops-alerts`, `invoices`, `support`; one incoming webhook (`NOTIFY_WEBHOOK_URL`) is shared and workflows override the channel per message.
